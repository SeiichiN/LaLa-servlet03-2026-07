## (1) 現在の設計について

### 良い点

サーブレットが

* パラメータ取得
* ロジック呼び出し
* JSPへフォワード

だけを担当している点は良いです。

```
Servlet
    ↓
SetDateLogic
    ↓
Person
```

という流れは分かりやすいです。

---

### 少し気になる点①

`SetDateLogic`という名前です。

実際には

```
文字列 → LocalDateへ変換
```

を行っています。

「日付をセットする」よりも

```
ParseBirthDateLogic
BirthDateService
PersonService
```

などの方が役割が伝わります。

あるいはもっと単純に

```java
LocalDate birthDate = LocalDate.parse(...);
person.setBirthDate(birthDate);
```

程度の処理だけなら、専用クラスを作らなくても構いません。

---

### 少し気になる点②

現在

```java
Person person = new Person(name, null);
logic.execute(birthday, person);
```

となっています。

私はこちらの方が好きです。

```java
LocalDate birthDate = logic.execute(birthday);

Person person = new Person(name, birthDate);
```

つまり

```
SetDateLogic
```

が

```
Person
```

を書き換えない設計です。

理由は

```
String
   ↓
LocalDate
```

という変換だけを担当するからです。

責務が一つになります。

例えば

```java
public class BirthDateParser {

    public LocalDate execute(String birthday) {
        DateTimeFormatter formatter =
            DateTimeFormatter.ofPattern("yyyy/MM/dd");

        return LocalDate.parse(birthday, formatter);
    }
}
```

とできます。

---

## (2) 例外処理はどこで行うか

ここが一番重要です。

私は

**(2-a)** をおすすめします。

つまり

```
Servlet
    ↓
Service
    ↓
例外
    ↑
Servlet
```

という流れです。

---

### 理由

日付エラーは

```
業務上予想される入力ミス
```

です。

例えば

```
2025/13/40
```

はユーザー入力として普通に起こります。

これは

```
異常終了
```

ではなく

```
入力エラー
```

です。

なので

```
サーブレットが受け止める
```

方が自然です。

例えば

```java
List<String> errors = new ArrayList<>();

try {
    LocalDate birthDate = logic.execute(birthday);
    Person person = new Person(name, birthDate);

    request.setAttribute("person", person);

} catch (DateTimeParseException e) {

    errors.add("誕生日を正しく入力してください");

    request.setAttribute("errors", errors);
}
```

この方がMVCらしいです。

---

## (2-b) Filterで処理するのは？

これはおすすめしません。

Filterは

例えば

* ログ
* 文字コード
* 認証
* 権限チェック
* 共通例外処理

など

**全ページ共通**

の処理を書く場所です。

一方

```
誕生日の入力エラー
```

は

```
PersonServletだけの話
```

です。

つまり

```
業務ロジック
```

なのでFilterに置かない方がいいです。

---

## BusinessExceptionは使うべき？

これは場合によります。

例えば

```
if (age < 18)
```

なら

```java
throw new BusinessException("18歳未満です");
```

はとても良いです。

しかし

```
LocalDate.parse(...)
```

が投げる

```
DateTimeParseException
```

は十分意味のある例外です。

わざわざ

```java
catch(DateTimeParseException e){
    throw new BusinessException(...);
}
```

にする必要はあまりありません。

---

### BusinessExceptionが活躍する場面

例えば

```java
if (person.getBirthDate().isAfter(LocalDate.now())) {
    throw new BusinessException("未来の日付は入力できません");
}
```

のように

**業務ルール違反**

を表すときです。

---

## 結論

* **(1)** MVCとしては概ね良い設計です。ただし、`SetDateLogic` は「文字列を `LocalDate` に変換する責務」に絞り、`Person` を直接変更せず `LocalDate` を返す設計の方が責務が明確になります。
* **(2)** 日付の入力ミスのような「予想される入力エラー」は、**サーブレットで捕捉してエラーメッセージを作成する方法（2-a）** が適しています。
* **Filter** は認証やログ、文字コード設定などアプリケーション共通の関心事を扱う場所であり、画面固有の入力チェックには向きません。
* **BusinessException** は「未来の日付は入力不可」「年齢は18歳以上でなければならない」といった**業務ルール違反**を表すのに有効です。一方、`LocalDate.parse()` が投げる `DateTimeParseException` は「入力形式が正しくない」という意味が明確なので、そのまま利用することが多いです。

## 良い点

サーブレットは非常に読みやすくなりました。

```java
Person person = new Person(name);

    person.setBirthDate(birthday);
    request.setAttribute("person", person);

    request.setAttribute("errorMsg", "日付が正しくありません");
}
```

「Personを作る」「誕生日を設定する」という流れが自然です。

また、例外をサーブレットで受ける設計も、前回お話ししたように私は良いと思います。

## 気になる点

問題は、このメソッドです。

```java
public void setBirthDate(String dateTxt)
```

`Person` の `birthDate` の型は

```java
private LocalDate birthDate;
```

ですよね。

つまり `Person` が本来持つデータ型は **`LocalDate`** です。

ところが

```java
person.setBirthDate("2025/07/05");
```

を受け付けるようになると、

`Person` が

* 文字列の形式
* 日付フォーマット
* 文字列から日付への変換

まで知ることになります。

これは少し責務が増えています。

---

JavaBeansのセッターは普通、


のように

**プロパティと同じ型を受け取る**

という約束になっています。

これなら

```java
person.setBirthDate(localDate);
```

だけです。

ここへ

```java
setBirthDate(String)
```

を追加すると、

「このBeanは文字列の解析までやるBeanなのかな？」

という印象になります。

## 結論

私は次のように評価します。

* **オーバーロード自体は問題ありません。**
* **サーブレットがすっきりした点は良い改善です。**
* ただし、`setBirthDate(String)` は `Person` に「文字列解析」という責務を持たせることになるので、設計上は少し気になります。
* 長期的な保守性を考えると、`Person` は `LocalDate` を扱うことに専念し、文字列から `LocalDate` への変換は別のクラス（あるいは少なくとも別名のメソッド）に任せる方が、責務の分離という点ではよりきれいな設計になります。

今回のコードは学習用としては十分良い出来ですし、実際の業務でも見かける書き方です。ただ、**「Beanはプロパティの型だけを扱う」「文字列の解析は入力層（サーブレットや変換クラス）が担当する」**という設計の方が、Javaではより一般的だと言えるでしょう。
